# Support Ticket Classification API

A small FastAPI service for creating and classifying support tickets using an LLM.

The API accepts a support ticket as free-form text. The ticket is then automatically classified by an LLM into a category, priority, responsible team, summary, and status. The original ticket and its classification are persisted in PostgreSQL.

## Live Application

**API:** [https://self-developed-testexercise.onrender.com/](https://self-developed-testexercise.onrender.com/)

**Swagger / OpenAPI documentation:** [https://self-developed-testexercise.onrender.com/docs](https://self-developed-testexercise.onrender.com/docs)

Example: ```curl -X POST 'https://self-developed-testexercise.onrender.com/tickets' -H 'accept: application/json' -H 'Content-Type: application/json' -d '{"message": "Das Produktivsystem ist nicht erreichbar"}'```

## Start and Usage

### Prerequisites

* Python 3.12+
* `uv`
* Docker (optional, for containerized execution)
* A PostgreSQL database
* An OpenAI API key

The application was developed using Neon as the hosted PostgreSQL database.

### Local development

Install dependencies:

```bash
uv sync
```

Create a `.env` file in the project root:

```env
DATABASE_URL=postgresql+psycopg://<user>:<password>@<host>/<database>?sslmode=require
OPENAI_API_KEY=<your-openai-api-key>
```

Start the application:

```bash
uv run uvicorn main:app --reload
```

The API is then available at:

```text
http://localhost:8000
```

Interactive API documentation:

```text
http://localhost:8000/docs
```

### Docker

Build the image:

```bash
docker build -t support-tickets .
```

Run the container:

```bash
docker run --rm \
  --env-file .env \
  -p 8000:8000 \
  support-tickets
```

The application will then be available at `http://localhost:8000`.

### Creating a ticket

The client only submits the ticket text:

```http
POST /tickets
Content-Type: application/json
```

```json
{
  "message": "Unser Produktionssystem ist seit heute Morgen nicht erreichbar. Mehrere Kunden können keine Bestellungen aufgeben."
}
```

The classification is performed by the LLM. A response looks like:

```json
{
  "ticketId": "T-1001",
  "category": "incident",
  "priority": "critical",
  "assignedTeam": "platform-operations",
  "summary": "Produktionssystem ist seit heute Morgen nicht erreichbar und mehrere Kunden sind betroffen.",
  "status": "manual_review_required"
}
```

Tickets can subsequently be retrieved using:

```text
GET /tickets
GET /tickets/{ticket_id}
```

## Architecture

The application follows a simple separation of responsibilities:

```text
Client
  │
  │ POST /tickets
  │ { message }
  ▼
FastAPI
  │
  ▼
TicketCreate
  │
  ▼
OpenAI / GPT-4 Turbo
  │
  │ category
  │ priority
  │ assigned team
  │ summary
  │ status
  ▼
Pydantic validation
  │
  ▼
Business rules
  │
  ▼
SQLAlchemy
  │
  ▼
Neon PostgreSQL
```

The API client is deliberately only responsible for providing the original ticket text. The classification fields are generated by the backend and are not accepted as user input.

## Important Assumptions and Decisions

### LLM classification

The LLM is responsible for determining:

* **Category:** `incident`, `request`, or `problem`
* **Priority:** `low`, `medium`, `high`, or `critical`
* **Assigned team:** one of the predefined support teams
* **Summary:** a short factual summary
* **Status:** normally `open` or `manual_review_required`

The model is instructed to only use predefined classification values.

### Validation

LLM output is not treated as trusted data.

The classification is validated using Pydantic enums and models before it is persisted in the database.

Additionally, important business logic is enforced in Python. In particular:

```text
priority = critical
        ↓
status = manual_review_required
```

This rule is therefore not dependent solely on the LLM following the prompt.

### Database

PostgreSQL was chosen because the application requires persistent relational storage and PostgreSQL is well supported by SQLAlchemy and available through hosted services such as Neon.

The ticket ID is generated using a PostgreSQL sequence. This avoids generating IDs by querying the latest ticket first, which could lead to duplicate IDs when multiple requests are processed concurrently.

Ticket IDs are exposed in the form:

```text
T-1001
T-1002
T-1003
```

### Configuration

Configuration is handled using Pydantic Settings.

Locally, values are loaded from `.env`. In the deployed application, the same settings are provided through the deployment platform's environment variables.

Secrets are not committed to the repository.

### Deployment

The application is packaged as a Docker image and deployed to Render.

The database is hosted separately on Neon PostgreSQL.

This keeps the application container stateless and separates application hosting from database hosting.

## What I Would Improve With More Time

Given more development time, I would consider implementing the following:

### Database migrations

Currently, the application uses SQLAlchemy's table creation mechanism during startup. For a production application, I would introduce **Alembic** for explicit database migrations and schema versioning.

### Automated tests

I would add:

* Unit tests for classification/business rules
* API tests for ticket creation and retrieval
* Database integration tests
* Tests for invalid or unexpected LLM responses

### More robust LLM error handling

The application could handle OpenAI API failures more explicitly, including:

* API timeouts
* Rate limits
* Temporary service failures
* Invalid model responses

A retry strategy and appropriate API error responses would improve reliability.

### Asynchronous processing

For a larger application, LLM classification could be processed asynchronously through a queue. This would prevent the API request from waiting for the LLM and would make the system more scalable.

### Authentication and authorization

The current API is intentionally minimal for the exercise. A production implementation would require authentication and authorization.

### Observability

I would add structured logging, request IDs, metrics, and error monitoring to make production issues easier to diagnose.

### Classification quality

I would create a small evaluation dataset containing representative support tickets and use it to measure classification accuracy and identify ambiguous cases.
